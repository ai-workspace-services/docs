# 运营管理面板：经营状态与账号处置工作台

> 设计稿：`01-operations-workbench.png`、`02-account-triage.png`、`03-billing-operations-overview.png`  
> 适用环境：UAT `https://console-uat.onwalk.net/`  
> 对应前端：`portal`  
> 版本：2026-08-10 / Build 2

## 1. 设计结论

将原 `/panel/management` 从“首页视频配置 + 权限矩阵 + 用户分组”的杂物间，重构为运营管理面板的入口容器。运营管理面板只服务于经营决策和账号处置，按工作任务拆成三类页面：

| 页面 | 路由 | 主要任务 | 对应设计稿 |
| --- | --- | --- | --- |
| 运营工作台 | `/panel/ops` | 看经营状态、发现异常、进入处置队列 | 图片 1 |
| 账号处置台 | `/panel/ops/accounts` | 检索单个账号，发权益、调套餐、调配额、调余额、清欠费 | 图片 2 |
| 计费运营总览 | `/panel/ops/billing/ledger` | 看收款、待入账、欠费、账单异常、对账和审批 | 图片 3 |

三个页面均归属于“运营管理面板”，不是普通用户工作区。

## 2. 访问控制

### 2.1 页面级权限

仅以下身份可以看到侧边栏入口并进入页面：

- 平台 root：后端 `root` 角色统一归一为 Portal `admin`。
- 管理员：`admin` / `administrator`。
- 运营者：`operator` / `ops`。

普通用户即使知道 URL，也必须在服务端返回 403，不能依赖前端隐藏菜单。没有运营角色的权限字符串不能单独绕过页面级角色门槛。

### 2.2 操作级权限

页面访问和高风险动作分离：

| 动作 | 管理员 / root | 运营者 | 审计要求 |
| --- | --- | --- | --- |
| 检索账号、查看订阅和余额 | 允许 | 允许 | 记录查询主体和目标账号 |
| 指派套餐、发体验额度、调整配额 | 允许 | 需 `admin.settings.write` | 原因必填，记录前后值 |
| 调整余额、清欠费 | 允许且需 `admin.billing.money.write` | 默认不允许，需显式资金权限 | 二次确认；真实资金变更必须有幂等键 |
| 发布价格 / 套餐 | 允许 | 需 `admin.settings.write` | 记录版本、发布时间、操作者 |
| 权限矩阵、黑名单 | 允许 | 允许 | 进入 `/panel/ops/system`，全量审计 |

所有变更统一写入审计日志：操作者、角色、目标账号、动作、原因、请求号、旧值、新值、结果、时间。金额和余额不得使用前端计算结果作为事实来源。

## 3. 信息架构

```text
运营管理面板
├── 运营工作台              /panel/ops
│   ├── 经营指标：MRR、活跃订阅、欠费名单、用量 TopN

│   ├── 账单例外、筛选、核对、导出
```

首页视频配置迁出运营工作台，保留在独立的内容 / 系统设置域；旧 `/panel/management` 在迁移期间显示迁移提示和新入口，不再继续堆叠新功能。

## 4. 三张设计稿的具体实现

### 图片 1：运营工作台

页面目标是回答“今天经营是否健康、现在先处理什么”。首屏顺序固定为：

1. MRR、活跃订阅、欠费金额、待处理事项四张指标卡；
2. 待处理队列，支持按账单异常、待入账、需审批筛选；
3. 近 7 天账号活动趋势；
4. 近期审计记录和账号活动概览。

指标卡必须显示数据时间、同比 / 环比口径和数据源状态。无数据时显示“待同步”，不能以 0 伪装成真实业务数据。

### 图片 2：账号处置台

页面目标是让运营者从账号问题直接完成处置。核心交互：

- 支持邮箱、UUID、用户名检索；状态、套餐、欠费和最近活动作为高级筛选；
- 列表突出“需要关注的账号”，展示账号、订阅、余额 / 状态、最近活动和处置入口；
- 右侧详情卡展示当前套餐、余额、配额使用、停机状态和最近账本；
- 指派套餐、发体验额度、调配额、调余额、清欠费均采用原因必填的确认弹层；
- 操作成功后刷新账号详情、账本和审计记录，失败时保留用户输入并展示后端错误。

### 图片 3：计费运营总览

页面目标是回答“收款是否入账、异常是否可解释、哪些变更需要批准”。首屏包含：

- 今日收款、待入账异常、欠费金额、需人工复核；
- 账单例外表格：支付单号、账户、异常类型、金额、账务状态、处理状态、更新时间；
- 右侧资金流、未入账金额、对账可信度和待审批变更；
- 下方近期审计记录与账户活动趋势；
- 支持按日期、异常类型、账务状态、处理状态和金额区间筛选，支持导出和逐条核对。

该页面必须接真实 billing / ledger 数据。PAYG “充值不入余额”在规划文档 09 的修复和验收完成前，充值、入账、余额更新、对账四个状态不得标记为已完成；运营台要明确显示阻断状态和异常数量。

## 5. 前后端重构规划

### Phase 0：权限与数据安全（P0）

- 在 Portal 路由守卫和每个 BFF 同时校验 `admin` / `operator` 角色；root 通过现有归一化进入 `admin`。
- 账号列表、账号详情、账单和审计接口全部禁止普通用户访问。
- 资金动作增加显式 `admin.billing.money.write` 权限、原因、幂等键和二次确认。
- 对 PAYG 充值链路建立“支付成功 → 账本入账 → 余额增加 → 对账完成”的可观测状态机。

### Phase 1：运营壳层与账号处置（P0）

- 新增 `/panel/ops` 路由组和统一运营侧边栏。
- 将现有 `/api/users` 作为过渡列表数据源，同时接入 `/api/admin/billing/accounts` 账号详情 BFF。
- 完成图片 2 的检索、详情、套餐、试用、配额、余额、清欠费流程。
- 每个 mutation 成功后刷新 SWR 数据并显示审计结果。

### Phase 2：经营总览（P0）

- 接入 MRR、活跃订阅、欠费、用量 TopN 和账号趋势真实聚合接口。
- 建立待处理队列，账单异常和需审批变更必须可跳转到具体账号或账单。
- 统一空状态、加载状态、部分数据可用状态和后端错误状态。

### Phase 3：计费运营（P0）

- 复用 `/panel/ops/billing/ledger` 承载图片 3 的计费运营总览和账单明细。
- 实现筛选、导出、逐条核对、对账可信度和审批队列。
- 充值链路修复前保留“待入账 / 余额未同步”告警；修复后用真实回归数据关闭告警。

### Phase 4：配置迁移与审计闭环（P1）

- 套餐 CRUD 迁移到 `/panel/ops/billing/plans`，支持价格版本和发布时间。
- 权限矩阵、黑名单迁移到 `/panel/ops/system`。
- 首页视频配置迁出运营管理面板，避免经营数据页面继续承担内容配置。
- 审计页 `/panel/ops/audit` 支持按操作者、目标账号、动作、结果和时间检索导出。

## 6. 验收标准

- root、管理员、运营者登录后能看到“运营管理”入口；普通用户不显示入口。
- 普通用户直接访问 `/panel/ops`、`/panel/ops/accounts`、`/panel/ops/billing/ledger` 均得到 403 / 禁止页，且 BFF 同样返回 403。
- 图片 1、2、3 的核心布局、层级和操作路径在 1440px 桌面宽度可用，窄屏不出现横向溢出。
- 所有金额、余额、MRR、欠费和入账状态均来自后端，禁止前端硬编码经营数字。
- 高风险操作原因必填、二次确认、幂等、可回滚或可补偿，并能在审计记录中还原前后状态。
- PAYG 充值回归用例覆盖支付、入账、余额增加、重复回调和对账；链路未通过前不得宣称发布完成。
- UAT 环境验证地址：`https://console-uat.onwalk.net/`；相关流水线：`https://github.com/ai-workspace-infra/platform-ops-toolkit/actions/runs/31367412474`。
