# 方案审计报告(2026-08-01)

> 审计对象:`feature-xray-usage-billing-portal-uat/` 规划(README + 01 架构契约 + 02 UAT 验收)
> 审计方法:逐条对照 8 个仓库的**实际代码、schema、compose、CI 配置**,不采信文档自述
> 结论:**有条件通过** —— 架构方向正确(Exporter 扇出、Billing 唯一写入、Accounts 聚合、Observability 旁路),但存在 3 个 Critical 缺陷,其中 1 个会在本方案的目标场景下**必然触发数据损坏**,必须先修复再进入开发。

## 一、总体结论:有条件通过

**架构判断正确的部分**(经代码验证):

- ✅ `xray-exporter` 已具备窗口 API `/v1/snapshots/window`(`since`/`until`/`cursor`/`has_more`),Billing 无需重写主流程
- ✅ Exporter 默认 72h SQLite 保留(`SNAPSHOT_RETENTION`),满足"中断后回补"
- ✅ 计数器重置已实现(负 delta → `reset_epoch++` → 新 checkpoint → 不回冲账本),与 §5.3.5 描述一致
- ✅ `traffic_minute_buckets` 唯一键含 `line_code`,用量**可**按线路拆分
- ✅ Observability 确为旁路:`collect-and-rate` 全链路不依赖任何遥测组件
- ✅ 计费链路不阻塞 Xray/Agent/登录:Billing 只读 Exporter + 写 PG,不参与配置下发

**必须先解决的阻塞项**:Critical 1/2/3(见下)。其中 **Critical 1 是代码缺陷,不是规划缺陷**,但规划的目标场景(双流量类型)会把它从"潜在"变成"必然"。

## 二、问题列表

### 🔴 Critical

#### C0. 「Billing 使用专属 DB」与现有共库实现存在**深度耦合**,直接拆库会把 Billing 推上登录与 Xray 配置的关键路径

> 本条针对追加要求「Billing 服务使用自己的专门 DB」。当前实现是 **Billing 与 Accounts 共用同一个 PostgreSQL**,规划 §2/§5.2 也是按共库写的("PostgreSQL Accounts accounting schema")。

**位置**
- `billing-service/sql/billing-service-schema.sql:9,23,39,51,66` — **5 处** `REFERENCES public.users(uuid) ON DELETE CASCADE`
- `accounts/internal/store/accounting_postgres.go` — Accounts 直接 SQL 读写 `account_quota_states` / `account_billing_profiles` / `traffic_minute_buckets` / `billing_ledger`
- `accounts/api/entitlements.go` — entitlement sync 写 `account_billing_profiles`、重置 `account_quota_states`、标记 arrears
- `accounts/internal/auth/middleware.go`(`RequireActiveUser`)+ `accounts/api/api.go`(`rejectIfBillingSuspended`)— **每个已认证请求**都读 `account_quota_states`
- `accounts/api/agent_server.go`(`listAgentUsers`)+ `api/internal_network_identities.go` — **Xray 配置下发链路**读 `ListSuspendedAccountUUIDs()`

**问题**
拆库会同时打断四类跨库依赖,其中两类在关键路径上:

| 依赖 | 现状 | 拆库后果 |
|---|---|---|
| 5 个外键 → `public.users(uuid)` | DB 强约束保证账户存在、级联删除 | **跨库无法建 FK**,孤儿账务行需应用层兜底 + 账户删除需跨服务清理 |
| Accounts entitlement sync **写** 配额/档案(P1) | 同库事务 | 需改为调用 Billing 写接口,**引入分布式一致性问题**(付款成功但配额未重置) |
| `RequireActiveUser` / `rejectIfBillingSuspended` **读** suspend 状态 | 同库单查询 | 每次登录态校验变成**跨服务调用** → Billing 故障 = **全站认证受影响** |
| `listAgentUsers` 读 suspended 集合(P1.5 断流) | 同库批量查询 | Xray 配置生成依赖 Billing 可用 → **Billing 故障影响 Xray 配置下发** |

后两条**直接违反本规划自己的隔离原则**(§2「Billing 故障不能让 Xray、Agent 或用户登录停止工作」、§10 故障矩阵中「Billing 不可用 → 用户连接/Xray 不受影响」)。也就是说:**如果按当前代码形态直接拆库,§10 的故障隔离矩阵将不再成立**。

**影响**
- 若不做补偿设计:Billing 从"旁路计量服务"变成**认证与 Xray 下发的强依赖**,可用性风险显著上升,且与 P1.5 已上线的断流机制冲突
- 若做补偿设计:需要引入状态复制或缓存,带来一致性与延迟问题,工作量远超本规划当前估算(规划未包含任何拆库工作项)

**基础设施现状:拆库在连接层已就绪**

`platform-ops-toolkit/docs/domains/web-saas/README.md:53` 已定义独立变量 `BILLING_DATABASE_URL`,并注明「**可以复用 `account_user`/`account`,也可以单独建一个账号**」。即:**改连接串就能换库,不需要改代码**。因此拆库的成本不在连接层,而在上面表格的四类数据耦合。

**一个决定性约束:§5.2 的单事务要求**

规划 §5.2 明确:「任何一次 `collect-and-rate` 必须在**单个数据库事务**中更新 checkpoint、minute bucket、ledger、quota state 和 source watermark」。**跨库无法做到单事务**。这条约束直接否决了"部分表拆走"的折中方案。

**方案评估(最小代价视角)**

| 方案 | 改动量 | 关键路径影响 | §5.2 单事务 | §10 隔离矩阵 | 结论 |
|---|---|---|---|---|---|
| **① 维持共库 + 逻辑隔离**(推荐) | **接近零**:仅新建独立 DB 角色 + 按表授权 | 无变化 | ✅ 保持 | ✅ 保持 | **最小代价,推荐** |
| ② 部分拆(私有事实表走新库,配额档案留 Accounts 库) | 中:Billing 双 DSN + 迁移 | 无变化 | ❌ **被打破**(bucket 与 quota 跨库) | ✅ 保持 | **不可行**,与 §5.2 冲突 |
| ③ 完全拆 + 配额状态复制回 Accounts | 大:迁移 + 复制通道 + 一致性处理 | 副本可读,不上关键路径 | ✅ 库内保持 | ✅ 保持(副本有延迟) | 真需要物理隔离时选这个 |
| ④ 完全拆 + 认证/下发实时调 Billing | 中 | ❌ **Billing 成全站单点** | ✅ | ❌ **矩阵失效** | **不可选** |

**推荐结论:本阶段维持共库(方案 ①)**

理由:
1. **拆库要解决的真实问题是"分钟桶数据量"**(见 H2),而它的正解是**滚存 + 保留策略**,不是换库。换库不减少数据量,只是换个地方涨。
2. 拆库会打断 5 个 FK、entitlement sync 的写路径、认证中间件与 Xray 下发的读路径——而这三者**都是 P1/P1.5 刚上线、已验证的链路**,重做的回归成本高于收益。
3. 若诉求是"故障爆炸半径"与"权限隔离",在**同库内**用独立 DB 角色 + 按表 `GRANT` 即可达成大部分收益,代价接近零:
   - 建 `billing_user`,只授予 6 张账务表的 `SELECT/INSERT/UPDATE`
   - Accounts 的 `account_user` 保留 `users` 等表全权 + 账务表按 §5.2 字段权责的最小授权
   - `BILLING_DATABASE_URL` 换成该角色的连接串(**只改配置**)
4. 若未来数据量或合规要求真的必须物理隔离,再走方案 ③,且**前提是先实现 PGMQ 消费者**(当前只有生产者、无消费者)作为复制通道。

**若最终仍决定拆库(方案 ③),规划必须补充:**
- §2 架构图与 §5.2 表格按两个库重画,标明每张表所属库
- §10 故障矩阵重新推导(尤其「Billing 不可用」一行,需说明副本延迟期间的行为)
- 数据迁移工作项:存量表搬迁、5 个 FK 改为应用层校验、账户删除的跨库级联清理
- P1/P1.5 已上线代码的改造范围:`entitlements.go`、`accounting_postgres.go`、`middleware.go`、`agent_server.go`

**无论选哪个方案,规划文档都需补充:**
- §2 架构图与 §5.2 表格需按"两个库"重画,明确每张表所属库
- §10 故障矩阵需重新推导(尤其"Billing 不可用"一行)
- 需新增数据迁移工作项(存量表搬迁、FK 替换为应用层校验、账户删除的跨库清理)
- P1/P1.5 已上线代码的改造范围需评估(`entitlements.go`、`accounting_postgres.go`、`middleware.go`、`agent_server.go`)

#### C1. Checkpoint 键缺少 `inbound_tag`,多 inbound 场景下计量数据损坏

**位置**
- `billing-service/sql/billing-service-schema.sql:7-18` — `traffic_stat_checkpoints PRIMARY KEY (node_id, account_uuid)`
- `billing-service/internal/service/service.go:235-267` — `GetCheckpoint(ctx, storageNodeID, sample.UUID)`
- `xray-exporter/internal/service/service.go:252` — 聚合键 `uuid + "\x00" + inboundTag`

**问题**
Exporter 的聚合键是 **(uuid, inbound_tag)**,一次 snapshot 中同一用户若有多个 inbound(xhttp + tcp),会产生**多条 Sample,各自持有独立的累计计数**。而 Billing 的 checkpoint 键是 **(node_id, account_uuid)**,不含 inbound_tag —— 这些样本共用同一行 checkpoint,互相覆盖:

```
Sample(xhttp, up=100) → checkpoint 空 → delta=100 → 写 bucket(line=xhttp) → checkpoint=100
Sample(tcp,   up=50 ) → checkpoint=100 → delta=-50 → 判定为"计数器重置" → 丢弃该样本, checkpoint=50
下一轮 Sample(xhttp, up=120) → checkpoint=50 → delta=70(真实应为 20)→ 超计 50 字节
下一轮 Sample(tcp,   up=60 ) → checkpoint=120 → delta=-60 → 又一次假重置 → 再丢弃
```

结果:**交替出现「假重置丢数据」与「超额计费」,`reset_epoch` 无限增长**,且 `traffic_minute_buckets` 按 line_code 分行存储的数据与 checkpoint 模型自相矛盾。

**影响**
- 用量数据错误(既有少计也有多计),**直接影响计费金额与配额扣减**,属数据损坏级
- 设计稿的「高速流量 / 普通 VPS 流量」双类型**必须依赖多 inbound 区分**,因此本方案一旦落地即触发,不是低概率边缘场景
- 若两个 exporter 实例(tcp/xhttp,节点侧实勘已确认存在)配置了相同 `EXPORTER_NODE_ID`,同样触发

**修复建议**
1. `traffic_stat_checkpoints` 主键改为 `(node_id, account_uuid, line_code)`,`line_code` 取 `inbound_tag`,空值用 `''` 兼容存量;`GetCheckpoint`/`UpsertCheckpoint` 同步加参数
2. 迁移脚本需处理存量行(默认 `line_code=''`);首次运行会对已有用户产生一次"新 checkpoint"效果,应选流量低谷执行并在 runbook 中说明
3. 补回归测试:同一 uuid 两个 inbound_tag 的 snapshot,断言两条 bucket 均写入、无 reset、delta 各自正确
4. **替代方案**(若不改 schema):Billing 在 `processSnapshot` 中先按 uuid 聚合所有 inbound 的计数再算 delta —— 但这样就**永久丧失按线路分流量的能力**,与设计稿冲突,不推荐

#### C2. 配额模型无法表达设计稿的「两档独立配额」

**位置**
- `billing-service/sql/billing-service-schema.sql:50-63` — `account_quota_states` PK=`account_uuid`,单字段 `remaining_included_quota BIGINT`
- `billing-service/sql/billing-service-schema.sql:65-77` — `account_billing_profiles` PK=`account_uuid`,单字段 `included_quota_bytes BIGINT`
- 规划 `01-architecture-and-contracts.md` §5.2(把两表列为"无需变更")、§6.1(响应体只有单套配额字段)

**问题**
设计稿要求**两条互相独立的配额进度条**:

| | 已用 | 总量 | 百分比 | 重置日期 |
|---|---|---|---|---|
| 高速流量 | 682.45 GB | 1,000 GB | 68.25% | 2025-06-01 |
| 普通 VPS 流量 | 1.23 TB | 2.00 TB | 61.50% | 2025-06-01 |

而 schema 中配额是**账户级单标量**:一个账户一行、一个剩余额度。用量侧虽可按 `line_code` 拆分,**配额侧无法拆分**。规划 §5.2 将两表标为现状可用、未识别此差距;§6.1 的响应契约同样只设计了单套 `includedQuotaBytes/usedBytes/remainingBytes`。

**影响**
- 按现状实现,Portal **只能显示一条合并进度条**,无法交付设计稿
- 若强行用两次查询拼装,配额总量、剩余、重置日期均无数据来源(见 C3)

**修复建议**
1. 引入配额维度表,例如 `account_quota_buckets(account_uuid, quota_key, included_bytes, remaining_bytes, period_start, period_end, ...)`,`quota_key` ∈ {`high_speed`,`vps`}(或以 `line_code` 分组映射)
2. 建立 **inbound_tag → quota_key 的映射配置**(放 `billing_plans` 或独立映射表),使 Billing 扣减时知道该扣哪一档
3. 保留现有 `account_quota_states` 作为账户级汇总(欠费/暂停状态仍是账户级),避免破坏 P1.5 的 `suspend_state` 链路
4. 规划文档 §5.2/§6.1 需相应补充;当前版本**不足以支撑设计稿**

#### C3. 无计费周期字段,「重置日期 / periodStart / periodEnd」无数据来源

**位置**
- `billing-service/sql/billing-service-schema.sql:50-63` — `account_quota_states` 无任何 period/reset 字段(只有 `effective_at`/`updated_at`/`last_rated_bucket_at`)
- 规划 §6.1 承诺返回 `periodStart` / `periodEnd`
- 设计稿显示「重置日期:2025-06-01(剩余 16 天)」

**问题**
配额重置周期在 schema 中不存在。`effective_at` 是状态生效时间,不是计费周期起点。Stripe 订阅侧虽有周期,但 `subscriptions` 表与配额表未建立周期映射,且 P1 的 entitlement sync 只在 `invoice.paid` 时重置配额、不记录周期区间。

**影响**
- 「重置日期 / 剩余 N 天」无法计算
- 按用户新要求的「订阅期内用量」聚合同样无区间可依

**修复建议**
1. 在配额表补 `period_start` / `period_end`(随 C2 的新表一并设计)
2. entitlement sync(accounts `api/entitlements.go` 的 `resetQuotaForPlan`)在重置时写入本期区间,取值来自 Stripe subscription 的 `current_period_start/end`
3. 免费/试用用户无 Stripe 订阅,需定义兜底周期规则(如自然月或 trial 起始 +7d)

`GET /api/account/usage/summary` **是已上线端点**,不是新增端点。规划给出的响应体与线上字段名几乎完全不同。若按规划字面实现,即为**破坏性变更**,违反 README「只新增」与 02 文档「现有 API 不改返回结构」的自述原则。

- 若确需新字段名,走 `/api/account/usage/summary?v=2` 或新端点,Portal 迁移完成后再废弃旧字段
- 规划 §6.1 应显式标注「以下为**新增字段**,现有字段保持不变」

#### H2. 无分钟→小时/天滚存与保留策略,与「DB 存汇总 + 数据量合理」的要求冲突

**位置**
- `billing-service/sql/billing-service-schema.sql` — 只有 `traffic_minute_buckets`,**无小时/日汇总表、无分区、无保留清理**
- 规划 §5.2 表格未包含任何汇总表

**问题**
用户明确要求:分钟级精度足够、DB 存**汇总**、需支持**每小时/每天/最近 7·10·30 天/订阅期内**、且**保持数据量合理**。当前只有分钟粒度事实表:
- 数据量 ≈ 用户数 × 节点数 × inbound 数 × 1440 行/天,无上限增长
- 「最近 30 天」「订阅期内」查询需扫描百万级行做实时聚合,`idx_traffic_minute_buckets_account_bucket` 只能部分缓解

**影响**
UAT 数据量小不会暴露,**生产规模下查询变慢、库体积失控**,属于上线后才爆发的风险。

**修复建议**
1. 新增 `traffic_hourly_buckets` / `traffic_daily_buckets` 汇总表(键含 `account_uuid, bucket_start, line_code`),由 `collect-and-rate` 事务内增量更新,或独立 rollup job
2. Accounts 的 timeseries 端点按 granularity 路由到对应粒度表(hour→hourly、day/7d/30d→daily)
3. 为 `traffic_minute_buckets` 定义保留期(建议 7~14 天)+ 定时清理或按月分区
4. 规划 §5.2 补充这三张表及写入权

#### H3. UAT 版本轴:验收要求与镜像 tag 契约**互相冲突**

**位置**
- 规划 README 决策 5 / §4:「UAT 使用不可变跨仓 snapshot tag;`latest` 不能作为可验收发布版本」
- `gitops/compose/web-saas/.env.uat:7-12`:注释明写「按 IMAGE-TAG-CONTRACT.md,**UAT 的 deploy_tag 恒为 latest**」,且 `ACCOUNTS_IMAGE`/`BILLING_IMAGE`/`CONSOLE_IMAGE`/`POSTGRESQL_IMAGE` 全为 `:latest`
- 同样情况见 `compose/agent-proxy/.env.uat`、`open-platform/.env.uat`、`ai-workspace/.env.uat`

**问题**
这**不是"忘了改"**,而是两份规范互相矛盾:`IMAGE-TAG-CONTRACT.md` 规定 UAT 恒用 latest(仅在需要钉死时换 `sha-<40>`),而本规划要求 UAT 必须不可变 snapshot。直接改 `.env.uat` 会违反镜像 tag 契约。

**影响**
- 验收无法复现:Portal/Accounts/Billing 可能来自不同构建
- 贸然修改会与平台既有交付规范冲突,引发跨仓不一致

**修复建议**
先在 `platform-ops-toolkit` 层面裁决二者关系(建议:**验收窗口内**临时钉 `sha-<40>`,验收通过后恢复 latest,并在 IMAGE-TAG-CONTRACT 中把这一例外写成正式条款),再动 `.env.uat`。规划 §4 应引用该裁决而不是单方面宣布。

#### H4. `region` 取自全局配置,非按节点/来源

**位置** `billing-service/internal/service/service.go:280` — `Region: s.cfg.DefaultRegion`;`internal/config/config.go:96` — 来自单个 `DEFAULT_REGION` 环境变量

**问题**
`traffic_minute_buckets.region` 参与主键并影响评率(`region_multiplier`),但取值是**整个 Billing 实例的全局常量**。多节点跨区域(设计稿含 日本/新加坡/美国/德国 四节点)时,所有节点用量都会被打上同一个 region。

**影响**
区域维度失真;若未来按区域差异化定价,评率错误。

**修复建议**
`region` 应来自 source 配置(`ExporterSource` 增加 `Region` 字段)或 Exporter snapshot 本身(Sample/Snapshot 增加 `region`);规划 §5.1 的 sample 契约建议显式加入 `region`。

## 五、建议新增的测试用例

**计量正确性(对应 C1,最高优先级)**
1. 同一 uuid、同节点、两个 inbound_tag 的 snapshot → 断言写入 2 条 bucket、各自 delta 正确、`reset_epoch` 不增长
2. 连续 3 轮上述 snapshot → 断言累计用量 == 各 inbound 增量之和(当前实现会失败)
3. 单 inbound 计数器回退 → 断言新 epoch、不写 bucket、账本不回冲

**幂等与重放**
4. 同一窗口重复 `collect-and-rate` → `WrittenMinutes=0 / ReplayedMinutes>0`,配额不二次扣减
5. Exporter 中断 2 小时后恢复 → 回补窗口,水位单调推进,无重复账本
6. node/env 不匹配 → 整页拒绝、水位**不**推进、错误计数+1

**配额与周期(对应 C2/C3)**
7. 两档配额独立扣减:高速流量耗尽不影响普通 VPS 流量余额
8. 周期滚动:`invoice.paid` 后 `period_start/end` 前移、两档配额各自重置

**故障隔离(对应 §10)**
9. Observability 全停 → `collect-and-rate` 仍成功、PG 正常落库
10. Billing 停机 → Xray 配置同步、Agent 心跳、用户登录不受影响;恢复后可回补
11. Exporter 停机 → Portal 用量卡显示 `stale` + 最后成功时间,二维码/订阅/账户安全区块正常
12. PG 不可用 → Portal 数据卡失败但**不影响**登录与二维码渲染

**兼容性(对应 H1)**
13. 契约测试:`usage/summary` 响应必须仍含 `totalBytes`、`remainingIncludedQuota`(防止字段被重命名)
14. Portal 在新字段缺失时渲染「—/暂不可用」,不抛错、不白屏

**数据量(对应 H2)**
15. 注入 30 天 × 多节点分钟数据 → 断言 7/30 天聚合查询在阈值内返回;断言分钟表按保留期被清理

**环境隔离(对应 L2)**
16. UAT 配置断言:不含生产域名(`svc.plus` 业务域)、不连生产 PG、Stripe 为 sandbox 模式

## 六、最终建议

**不建议立即进入完整开发;建议按下述顺序分两步走:**

**Step 0(必须先做,约 2~4 天)**
1. 修复 **C1**(checkpoint 加 line 维度)+ 补测试用例 1~3 —— 这是**独立的现网缺陷修复**,即使本方案不做也应修
2. 裁决 **H3**(UAT tag 契约冲突)与 **M3**(实时数据走 Accounts 代理还是 Portal 直连)—— 纯决策
3. 补充规划:**C2/C3 的配额与周期模型设计**、**H2 的汇总表与保留策略**、**H1 明确"只加字段"**

**Step 1(Step 0 完成后)**
按规划 02 文档的 Phase 0→4 推进。Phase 1 的只读链路在修完 C1 后即可动工;Phase 3 的 Portal 双配额展示依赖 C2/C3 落地。

**可以并行、不受阻塞的部分**:Observability 旁路接入(Phase 2)、Exporter 指标补充、Accounts 只读端点(`nodes`/`timeseries` 骨架)。
